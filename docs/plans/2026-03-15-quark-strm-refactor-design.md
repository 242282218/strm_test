# Quark STRM 保守重构设计

- 日期：2026-03-15
- 范围：仅 `quark_strm`
- 目标：在不改变现有功能逻辑的前提下，完成分层保守重构，消除中文乱码，统一配置入口，清理弃用死代码，并在每一步优化后执行最小可行验证。

## 1. 背景与目标

当前主应用同时包含 FastAPI 后端与 Vue 3 + TypeScript 前端，已具备配置页、系统配置 API 和统一配置服务，但存在以下问题：

1. 配置入口分散，单一配置中心尚未完全建立。
2. 配置模型与前端表单之间仍有映射空洞，部分配置只能通过原始 JSON 或文件侧维护。
3. 代码中存在历史兼容分支和潜在重复实现，影响长期维护。
4. 已发现业务源码中的中文乱码，例如 `app/config/settings.py` 中的 Emby 配置说明文本。
5. 需要在“功能逻辑不变”的强约束下进行性能与结构优化，因此必须采用小步验证策略。

本次设计采用“方案 A：分层保守重构”，优先保证稳定性、可验证性与可回滚性。

## 2. 约束与非目标

### 2.1 强约束

1. 仅处理 `quark_strm`，不处理仓库根目录及其他子目录。
2. 不改变产品行为，不顺手增加新功能。
3. 不改变现有外部接口语义，尤其是配置读写、敏感字段脱敏与保留原值逻辑。
4. 每完成一类改动，必须立即执行该类改动对应的最小验证。
5. 死代码仅在“已验证无引用、无入口、无测试依赖、无配置契约依赖”后才允许删除。

### 2.2 明确排除项

1. 不处理仓库根目录的脚本、配置与辅助文件。
2. 不处理用户本地 shell 环境文件问题，例如 `.bashrc` 编码异常。
3. 不进行架构重写，不引入新的配置系统或新的运行时依赖作为核心方案前提。

## 3. 当前关键链路

本次重构围绕以下关键链路建立基线与回归护栏：

- 前端配置中心：`web/src/views/ConfigView.vue`
- 前端配置 API：`web/src/api/systemConfig.ts`
- 后端系统配置 API：`app/api/system_config.py`
- 后端统一配置服务：`app/services/config_service.py`
- 后端配置模型真相源：`app/config/settings.py`
- 已有后端配置测试：`tests/test_system_config_api.py`
- 已有前端配置 API 测试：`web/src/api/systemConfig.spec.ts`

## 4. 总体策略

### 4.1 Round 0：建立基线

在真正改代码前，先确认当前关键链路具备最小可回归能力：

1. 后端优先跑配置链路测试，确认系统配置 API 与配置服务工作正常。
2. 前端优先跑配置 API 测试，确认配置接口封装与调用契约稳定。
3. 补跑前端 `type-check` 与 `build`，确认当前主界面与配置页可以正常构建。

该阶段不做功能修改，只建立“当前行为快照”。

### 4.2 Round 1：乱码与编码治理

目标是消除业务源码中的中文乱码、错误编码文本和不可读字符，但不修改任何业务流程。

执行原则：

1. 先做只读扫描，再做定点修复。
2. 统一业务源码为 UTF-8。
3. 只修复文本层问题，不改字段名、接口结构和业务逻辑。

已确认问题示例：

- `app/config/settings.py` 中存在乱码文本“鍏ㄥ眬Emby 配置”。

### 4.3 Round 2：配置中心收敛

目标是将 `web/src/views/ConfigView.vue` 建成单一配置中心。

设计原则：

1. `ConfigView` 作为唯一配置入口，按分组或标签页组织配置。
2. 后端继续以 `AppConfig` 作为唯一配置真相源，不在前后端维护两套独立配置定义。
3. 保留“高级 JSON 配置”作为兜底入口，避免低频字段暂未表单化时失去可编辑能力。
4. 业务页可保留业务操作和结果展示，但不再承担配置主入口职责。
5. 敏感字段继续沿用脱敏展示、空值保留原值、掩码回填恢复等现有安全语义。

建议收敛的配置分组：

1. 基础运行：数据库、日志、全局超时、扩展名。
2. 夸克与目录映射：`quark`、`endpoints`。
3. Emby。
4. WebDAV / AList。
5. 通知：Telegram / WeChat。
6. AI Providers / TMDB。
7. 安全与 CORS。
8. 高级 JSON。

### 4.4 Round 3：死代码清理

目标是在不改变行为的前提下减少历史包袱。

清理原则：

1. 只删除已证明无入口、无引用、无测试依赖、无配置契约依赖的代码。
2. 不做猜测性删除。
3. 每次只处理一小类，删除前先做引用核验，删除后立即跑受影响测试。

首轮重点核验对象：

1. 前后端新旧 AI 配置并存链路：
   - `app/api/system_config.py` 中 `ai-models` 与 `ai-providers` 双轨逻辑
   - `app/config/settings.py` 中旧 AI 配置到统一 `ai.providers` 的迁移逻辑
   - `web/src/api/systemConfig.ts` 中旧接口与新接口并存情况
2. 配置中心收敛后，业务页中仅用于“配置输入”的重复代码是否仍有必要存在。
3. 明确将 `.venv`、`node_modules`、`dist`、`htmlcov`、`playwright-report`、`test-results` 排除在业务死代码判断之外。

删除顺序建议：

1. 前端重复配置调用与重复配置表单片段。
2. 后端确认不再需要的兼容分支。
3. 已确认无引用的服务、工具和辅助模块。

### 4.5 Round 4：保守性能优化

目标是在不改变逻辑的前提下进行小幅优化。

允许的优化范围：

1. 去除重复请求。
2. 去除重复计算。
3. 去除不必要的序列化与反序列化。
4. 降低前端冗余渲染。
5. 合并可以等价合并的轻量逻辑。

禁止事项：

1. 不做架构重写。
2. 不改变外部接口行为。
3. 不因性能优化而引入新的行为分支。

## 5. 测试与验证策略

### 5.1 基线测试

Round 0 建议执行：

1. 后端：`tests/test_system_config_api.py`
2. 前端：`web/src/api/systemConfig.spec.ts`
3. 前端：`vue-tsc` / `type-check`
4. 前端：`vite build`

### 5.2 每一步改动后的最小验证

1. 乱码修复后：
   - 后端配置链路测试
   - 前端配置 API 测试
   - 前端类型检查

2. 配置中心改造后：
   - 后端配置链路测试
   - 前端配置页/配置 API 测试
   - 前端构建验证

3. 死代码删除后：
   - 仅跑受影响模块测试
   - 补一次前端 `type-check` / `build` 或后端相关回归

4. 性能优化后：
   - 受影响模块测试
   - 最终综合回归

### 5.3 收尾验证

最终建议执行：

1. 后端配置相关与关键 API 回归。
2. 前端 `vitest run`。
3. 前端 `vue-tsc`。
4. 前端 `vite build`。
5. 若配置页交互变化较大，再补一条 Playwright 冒烟，只验证“打开配置页、加载、保存成功”主路径。

## 6. 验收标准

满足以下条件才算本次重构完成：

1. 功能逻辑保持不变。
2. 已发现和新增发现的业务源码中文乱码全部清理完成。
3. 配置可从单一配置中心完成设置，高级 JSON 仍作为兜底可用。
4. 已验证的死亡代码已清理，且无回归。
5. 每一步优化后均有对应最小验证记录。
6. 最终前后端均能通过构建与测试。

## 7. 实施顺序摘要

1. 建立基线。
2. 修复乱码与编码问题。
3. 收敛配置中心。
4. 清理死代码。
5. 做保守性能优化。
6. 执行最终回归。

## 8. 风险控制

1. 所有改动按小步提交思路组织，每步只解决一类问题。
2. 任何兼容逻辑删除前，必须先证明真实入口已经迁移或不存在。
3. 配置中心改造阶段始终保留 JSON 兜底，降低配置遗漏风险。
4. 若任一步测试失败，优先修正该步问题，不跨步叠加修改。
